# Payment Failure SOP

## 目标

本文档定义支付失败原因分析的通用流程，供 Zeus Payment Agent 在 V4 和 V5 阶段使用。Agent 应根据订单、支付流水、支付日志、失败规则和知识库文档输出可解释、可追踪、可执行的分析结论。

## 分析输入

Agent 分析支付失败时应优先收集以下信息：

- 订单号。
- 订单状态。
- 订单金额和币种。
- 用户 ID。
- 支付方式。
- 支付渠道。
- 最近支付流水。
- 内部失败码。
- 渠道错误码。
- 渠道错误信息。
- 支付日志事件序列。
- Trace ID。
- 已命中的失败规则。

## 分析优先级

1. 订单状态和支付流水状态优先。
2. 明确失败码优先。
3. 渠道错误码优先于自然语言错误描述。
4. 支付日志中的失败事件优先于订单表里的概括字段。
5. 知识库文档用于解释和补充建议，不替代事实数据。
6. 如果证据不足，应明确说明“不足以判断”，不要编造原因。

## 失败类型

| 原因类型 | 说明 | 常见证据 | 处理建议 |
| --- | --- | --- | --- |
| `USER` | 用户行为或用户账户导致 | 用户取消、卡信息错误、账户受限 | 引导用户重试或更换支付方式 |
| `BALANCE` | 余额或额度不足 | `INSUFFICIENT_FUNDS`、`BALANCE_NOT_ENOUGH` | 建议充值、换卡或更换支付方式 |
| `RISK` | 风控拒绝 | `RISK_REJECTED`、渠道风控码 | 建议更换支付方式，避免频繁重试 |
| `CHANNEL` | 渠道明确拒绝或渠道业务限制 | PayPal 拒绝、银行拒绝 | 查询渠道说明，必要时切换渠道 |
| `NETWORK` | 网络、超时、回调延迟 | `TIMEOUT`、请求耗时过长、无回调 | 主动查询渠道状态，必要时补单 |
| `SYSTEM` | 商户系统、配置或程序异常 | 签名错误、验签失败、内部异常 | 查看应用日志、配置和 Trace |
| `UNKNOWN` | 证据不足 | 没有流水、没有日志、没有错误码 | 补充日志、查询渠道状态、完善规则 |

## 通用排障流程

### Step 1 确认订单

先查询订单表，确认订单是否存在，以及订单当前状态。

如果订单不存在：

- 不要继续编造原因。
- 提示订单未找到。
- 建议确认订单号或查询时间范围。

如果订单成功：

- 不要输出失败归因。
- 可以说明订单当前已成功。
- 如果用户仍认为失败，建议检查是否存在多次支付尝试或前端展示延迟。

### Step 2 查询最近支付流水

支付流水是失败分析的核心证据。需要确认：

- 这笔订单是否发起过支付。
- 是否存在多次支付尝试。
- 最近一次支付尝试使用了哪种支付方式。
- 最近一次支付尝试是否失败、取消、超时或成功。

如果没有支付流水：

- 说明可能尚未发起支付。
- 也可能是流水未落库。
- 建议检查创建支付流水的业务日志。

### Step 3 匹配失败规则

优先使用内部失败码和渠道错误码匹配 `payment_failure_rule`。

规则匹配优先级：

1. method + channel + failure_code + channel_error_code。
2. method + channel + failure_code。
3. method + failure_code。
4. failure_code。
5. channel_error_code。
6. 通用规则。

命中规则后，Agent 应输出：

- 原因类型。
- 原因说明。
- 建议动作。
- 关键证据。
- 置信度。

### Step 4 读取支付日志事件序列

支付日志用于判断失败发生阶段：

- `CREATE_PAY` 失败：本地创建支付单失败。
- `REQUEST_CHANNEL` 失败：请求渠道前或请求渠道时失败。
- `CHANNEL_RESPONSE` 失败：渠道明确返回失败。
- `CALLBACK` 失败：异步回调处理失败。
- `QUERY` 失败：主动查询渠道状态失败。
- `ERROR`：本地系统异常。

日志事件序列可以帮助判断：

- 是用户没完成支付，还是系统没处理成功。
- 是渠道拒绝，还是网络超时。
- 是回调没来，还是回调来了但验签失败。
- 是否需要补单。

### Step 5 输出分析结论

支付失败分析回答建议包含：

- 订单号。
- 支付方式和渠道。
- 当前状态。
- 失败原因类型。
- 置信度。
- 关键证据。
- 建议处理动作。

## 回答格式建议

推荐格式：

```text
这笔订单支付失败，初步判断为【原因类型】。

关键证据：
- ...
- ...

建议处理：
- ...

置信度：HIGH / MEDIUM / LOW
```

## 置信度规则

| 置信度 | 条件 |
| --- | --- |
| `HIGH` | 命中明确失败规则，并且流水或日志中有对应错误码 |
| `MEDIUM` | 未命中规则，但流水、日志或错误文本可以推断 |
| `LOW` | 订单、流水或日志缺失，证据不足 |

## 不应做的事

- 不要在没有订单数据时编造订单状态。
- 不要在没有支付流水时断言渠道失败。
- 不要在超时场景直接建议用户重复支付。
- 不要把回调处理失败说成用户支付失败。
- 不要暴露完整银行卡号、身份证号、手机号、密钥、证书等敏感信息。

## 生产化建议

- 失败规则应持续维护，并记录命中率。
- 每次 Agent 分析应记录输入、命中规则、证据和最终回答。
- 对低置信度结论应提示人工复核。
- 对高频失败码应进入日报和异常检测。
- 对单渠道失败率突增应触发自主调查流程。
